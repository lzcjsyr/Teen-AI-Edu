# 明细自动分类

## 目标与边界

把一份结构可能变化的明细表，整理为一份交付物：

1. 已分类明细表：保留原始明细，并增加“科目代码”和“科目名称”。

分类标准是本 Skill 的固定业务规则，详见 `references/classification_rules.md`。不能因为输入文件换了名称、列顺序或出现新商品，就修改代码、科目名称或科目边界。若输入内容明显不属于这套标准，应说明不适用，不要擅自新增科目。本 Skill 只负责分类与回写；汇总和图表分析属于后续加工，由用户在下一步单独提出。

## 最重要的工作原则

### AI 负责理解，程序负责执行

AI 先读取文件样本，理解表格结构和业务语义，再把明确的结构信息交给通用读写逻辑。读写逻辑只负责：读取指定工作表和区域、按映射回写并输出文件，不负责猜测业务含义。

不要制作针对某一个文件名、某一列字母或某一个固定表头行的脚本。任何可复用的辅助程序都必须通过参数或结构化配置接收以下信息：

- 输入文件路径和文件类型
- 工作表名称或数据页
- 表头所在行、数据起始行
- 商品名称列、金额列、日期列、数量列等字段映射
- 新增列的插入位置
- AI 生成的商品分类映射

这样文件改成 `.xlsx`、工作表换名、表头前多几行说明，或“商品名称”改成“品名/货物名称”，都不需要重写脚本。

### 不凭文件名和列号做假设

每次处理都要先确认：

- 实际使用的输入文件，而不是默认寻找某个固定文件名
- 有效数据所在的工作表，而不是默认第一张表
- 表头行和数据起始行
- 商品名称字段，以及金额、日期、数量等可选字段
- 是否存在合计行、空行、说明行、重复表头或多个数据区

字段名称可以不同。应结合表头文字、前几行样本、数据类型和相邻列的含义判断。例如“品名”“商品名称”“货物名称”“物料名称”可能都指向商品名称字段，但不能只凭字符串匹配就直接决定。

## 标准工作流程

### 第 1 步：发现并检查输入

先列出用户指定目录中的候选文件，确认扩展名、文件大小和修改时间。只处理用户指定或明确相关的文件，不覆盖原始文件。

按格式选择通用读取方式：

- `.xls`：使用 `xlrd` 读取
- `.xlsx`、`.xlsm`：使用 `openpyxl`；如需保留宏，先说明输出限制
- `.csv`、`.tsv`：使用标准库或等价的表格读取工具，并检测编码、分隔符和引号

读取时先获得工作表列表、行列范围和少量原样样本，再决定目标数据区。不要为了适配示例而把“第 2 行”“第 5 列”写进固定代码。

### 第 2 步：建立结构说明

在正式分类前，形成一份临时的结构说明或内存映射，至少包括：

```json
{
  "input_file": "原始文件路径",
  "sheet": "实际数据页",
  "header_row": 0,
  "data_start_row": 1,
  "columns": {
    "item_name": 4,
    "amount": 8,
    "date": 1,
    "quantity": 6,
    "unit": 7
  },
  "insert_after": 8,
  "notes": ["跳过标题行、空行和合计行"]
}
```

这里的数字只是当前文件的识别结果，不是写死的规则。交付说明中要告诉用户实际识别到了什么；如果存在两个可能的商品名称列，先根据样本判断，仍无法判断时再暂停并说明。

### 第 3 步：按固定标准进行语义分类

完整阅读 `references/classification_rules.md` 后，对商品名称进行语义判断：

1. 先保留原始商品名称，再做轻量标准化，例如去除首尾空格、换行、重复空格和明显的格式噪声。
2. 对标准化后的唯一商品名称进行分类，再把结果映射回所有明细行，避免同一商品在不同行得到不同科目。
3. 根据商品的本质用途和类别判断，不只依赖某个关键词；品牌、产地、规格、包装方式和加工方式通常是修饰信息。
4. 每一条有商品名称的明细都必须得到既有 7 个科目中的一个代码和名称。
5. 对不确定的商品仍然选择最接近的既有科目，同时单独记录“需要人工复核”的商品、采用的科目和判断依据。不要把“待人工确认”写成新的科目。

如果输入目录中已有“已分类”“分类明细”或其他明确带有科目代码/科目名称的参考成果，应先把它当作当前业务的标注样本：

- 对相同或轻量标准化后相同的商品名称，优先沿用参考成果中的分类，保证同一业务口径前后一致。
- 参考成果只能帮助解决已有商品的具体边界，不能用来新增、改名、合并或拆分 7 个固定科目。
- 对参考成果中没有出现的新商品，才按固定分类规则进行语义判断。
- 如果参考成果与固定规则看起来冲突，不要悄悄改其中一方；保留固定科目，并把冲突列入复核清单。

这一步尤其重要：分类脚本不能用粗略关键词或自己猜测的启发式规则替代 AI 的商品理解，也不能因为总金额能够对上，就忽略商品在不同科目之间被错分。

建议内部保留如下分类映射，便于核对：

```json
{
  "标准化商品名": {
    "code": "1403.01.01",
    "subject": "荤食类",
    "confidence": "high",
    "review": false,
    "reason": "商品本质属于肉类"
  }
}
```

### 第 4 步：校验后回写明细表

回写前先做校验，不要只检查文件是否成功保存：

- 有商品名称的明细行是否全部获得科目代码和科目名称
- 原始明细行数、日期、商品名称和金额是否与输入一致
- 识别到的金额列是否可以求和；金额是否存在文本、空值或异常负数
- 分类后各科目金额合计是否等于原始有效明细金额，差额必须解释
- 如果目录中有参考分类成果，当前分类的科目数量、金额汇总和重点商品映射是否与参考口径一致；出现差异时先复核商品映射，再交付
- 合计行、空行和说明行是否被错误地当成商品明细
- 是否有重复表头、重复商品名称或无法识别的异常记录

输出时：

- 不覆盖原始文件；优先在同目录生成新的 `.xlsx`
- 保留原始数据顺序和主要单元格值
- 新增“科目代码”“科目名称”两列，插入位置根据当前表格结构选择，不固定为某个列号
- 对非数据行保持空白或原样，不把分类值填进标题和合计行
- 尽量保留原表的日期、数字和基本格式；如果 `.xls` 转为 `.xlsx` 导致部分格式无法保留，要在说明中写明

输出文件名根据输入文件名生成，例如：

- 明细表：`{输入文件名}_已分类.xlsx`

不要把“饭堂4月”或其他示例名称写进固定脚本。若目标文件已存在，应生成不覆盖原结果的新文件，或先向用户说明。

## 交付前检查

完成后至少检查：

1. 已分类明细表真实存在，且文件名由输入文件动态生成。
2. 有商品名称的明细行都获得了科目代码和科目名称。
3. 随机抽查不同科目的商品，分类代码和名称匹配。
4. 复核清单包含所有不确定项；没有为了让覆盖率看起来完整而偷偷新增科目。
5. 没有覆盖原始文件，也没有把路径、列号或示例金额硬编码到通用流程里。

## 运行环境提示

首次处理 `.xls` 时，确认已安装 `xlrd`；处理 `.xlsx`、`.xlsm` 时确认 `openpyxl` 可用。依赖安装只能解决文件格式读取问题，不能替代 AI 对表结构和分类语义的判断。

已知坑位：

- `xlrd.open_workbook` 的 `logfile` 参数在函数定义时就绑定了当时的 `sys.stdout`，因此临时重定向 `sys.stdout` 拦不住 `OLE2 inconsistency` 一类告警，告警会混入 stdout 让 JSON 解析失败。必须显式传 `logfile`。
- 脚本给出的 `suggestions` 只是提示。含“名称”的列可能是“单位名称”“客户名称”，不是商品名称；必须结合样本行确认，不要直接采信。
- `.xls` 经 `openpyxl` 输出为 `.xlsx` 后，整数形态的浮点数（如 `5.0`）会以 `5` 读回。数值本身不变，核对时应按数值比较，不要按字符串比较，否则会误判为内容不一致。
