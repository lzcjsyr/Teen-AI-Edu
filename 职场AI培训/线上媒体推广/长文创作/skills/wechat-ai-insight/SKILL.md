# 微信公众号 AI 洞察写作

## 适用场景

- 用户提供了本地参考材料（报告、文章、数据、研究笔记等），需要基于这些材料撰写一篇 AI 领域的深度公众号文章。
- 用户已经把文章写好，只需要做公众号排版和 DOCX 导出。
- 重写一篇只有新闻复述、来源薄弱或判断太空泛的现有草稿。

成稿必须基于用户提供的材料展开，回答"这些材料揭示了什么、意味着什么"，不能停留在材料复述、情绪评论或泛泛而谈的常识堆砌。
成稿默认必须把抽象概念翻译成具体场景、具体动作或具体商业例子，避免概念空转。
成稿默认还要照顾手机阅读场景，但不能为了拆段而拆段，导致信息密度被打散。
写作流程默认采用"先成文，再重新分段，最后排版"，不要在起草阶段靠机械控字数来决定段落。

## 标题要求

- 文章主标题不超过 17 个汉字或等价字符。
- 章节标题不超过 14 个汉字或等价字符。
- 标题默认追求简洁、真诚、清楚，不追求夸张、悬念式或营销式表达。
- 如果原始标题过长，默认先压缩再进入排版或写作流程。
- 若一个判断需要靠很长的标题才能成立，通常说明正文结构还不够清楚，应先重写论证而不是继续拉长标题。

标题风格默认遵循这些理解：
- 深度、严谨、尊重事实、真诚的内容，不需要靠刻意营销来吸引注意。
- 最好的"传播性"来自通俗易懂、有用有料，而不是标题里堆判断、堆情绪、堆刺激性词语。
- 标题应帮助读者快速理解文章谈什么，而不是用力"抓人"。

## 重分段步骤

- 正文先按论证完整性写完，再单独做一轮重新分段。
- 重新分段时，目标不是把段落切短，而是让每段只承担一个清楚的推进动作。
- 重分段后，段落节奏要有起伏。长段落和短段落应自然穿插、错落出现，避免一屏连续都是厚段，也避免一屏连续都是碎段。
- 段落长度应适中，不要太长，以适配手机阅读的视觉习惯。
- 默认优先保留信息密度，再优化视觉节奏；不要为了显得轻快，把一句完整论证硬拆成三四个碎段。
- 短段落只用于强调、转折、承上启下或落结论，不应成为正文的主要形态。
- 如果一个自然段里同时承担了"引入背景、展开例子、给出判断"三个动作，通常应该拆开。
- 如果相邻两段表达的是同一个动作，只是被机械切开，通常应该合并。
- 重新分段时优先处理三类厚段：
  1. 事实信息与解释判断混在一起。
  2. 例子与结论挤在同一段。
  3. 并列信息过多，读者一屏扫不清重心。
- 重分段后，默认再做一次句子级清理，删掉多余连接词、重复判断和拖长节奏的修饰语。

## 标点要求

- 尽量避免使用双引号和破折号。
- 如果确实需要表示强调、引用或特定说法，优先使用方引号「」；不要使用中文双引号""。

标题压缩默认按这个顺序处理：
- 先删副词和情绪词，比如"重磅、彻底、终于、真正、最、全面、深度"。
- 再删重复限定语，比如"在今天这个阶段""从某种意义上说""一个值得关注的问题是"。
- 再把并列判断压成一个主判断，避免一个标题同时说两三件事。
- 再把解释性成分放回导语或正文，不塞在标题里。
- 如果仍然超长，优先保留"对象 + 变化 / 判断"，删掉修辞。

可执行判断：
- 主标题最好让读者一眼知道"这篇文章在解释什么变化"。
- 章节标题最好让读者一眼知道"这一节到底回答什么问题"。
- 如果标题像广告语、海报文案或短视频封面文案，默认重写。

## 使用方式

### 方式一：本地材料创作

当用户提供了本地参考材料（文件路径、粘贴的文本、PDF、笔记等），默认流程是：

1. 先阅读和分析用户提供的材料，提取核心信息、关键数据和判断。
2. 从材料中提炼出一个值得回答的"机制问题"——这篇文章到底要解释什么。
3. 以材料为证据底座，按现有写作、配图、导出流程完成文章。
4. 如果材料不足以支撑一篇文章的论证，应主动提示用户补充更多材料，而不是靠空泛发挥填满篇幅。

推荐指令模板：

```text
参考以下材料，写一篇公众号文章：

材料一：/path/to/report.pdf
材料二：（直接粘贴文本）
```

### 方式二：仅排版

如果文章已经写好，只需要排版，不需要写作。

最方便的输入方式：
- 在对话框里先输入：`仅排版。`
- 然后把文章原文直接粘贴在后面
- 如果有本地图片，再补充图片目录路径

默认理解：
- 不重写正文，不补写观点，不扩写内容
- 只做结构映射、图片整理和 `.docx` 导出

推荐指令模板：

```text
仅排版。

下面是文章原文：
（把正文直接粘贴在这里）
```

如果还要配合本地图片，可用：

```text
仅排版。
图片目录：/path/to/images

下面是文章原文：
（把正文直接粘贴在这里）
```

## 默认交付

- 所有生成的微信公众号长文创作项目，必须以独立的文件夹统一存放在当前工作目录下的 `output/` 文件夹中。
- 项目文件夹命名格式为：`短标题-月日`（只带月日，相对路径表示，例如 `output/裁员跑在AI前面-0526/`）。
- 项目文件夹内必须包含：研究笔记（如有）、`article.md`、`images/`，以及最终生成的同名 `.docx` 编译成品（例如 `裁员跑在AI前面.docx`，文件名必须与文章主标题完全一致）。
- 成稿默认 1500 到 2500 字，优先约 2000 字
- 正文不要重复主标题
- 文末保留"信息来源"，只写题名与作者或作者单位，不展示 URL
- DOCX 格式规则见 [references/wechat-docx-format.md](references/wechat-docx-format.md)

## 工作流

1. 建项目文件夹，所有素材和产物都放进去，图片统一放 `images/`。
2. 如果用户提供了本地参考材料，先阅读分析材料，提取核心信息。
   把材料中的核心判断、关键数据、机制变化提炼出来，作为写作的证据底座。
   如果用户已经给了明确题目，直接进入下一步。
3. 把题目改写成值得回答的"机制问题"。
4. 先建证据底座。
   证据要求见 [references/source-policy.md](references/source-policy.md)。
5. 先写完整正文，再处理插图。
   文章结构见 [references/article-playbook.md](references/article-playbook.md)。
   写正文时，凡是出现"机制、护城河、工作流、责任、信任、效率、闭环"这类抽象词，默认都要配一个普通读者能立即理解的例子。
5.5 完稿后单独做一轮重新分段。
   顺序固定为"成文 -> 分段 -> 排版"。
   重分段时不要改动文章核心判断，不要新增论点；只调整段落边界、句群归属和少量衔接句。
   分段标准是：一段只做一件事。背景归背景，例子归例子，判断归判断，结论单独落段。
   遇到厚段，优先从"转折后、例子前、结论句前、视角切换处"拆开；遇到碎段，优先按同一动作合并。
   重分段后统一检查标点，尽量避免双引号和破折号；确需引号时统一改为「」。
6. 统一做图片计划并选择配图方式。
   默认走 API 文生图；当主体足够具体且真实照片更合适时，可切换到联网下载图片模式；只有当用户明确要求本地解释图或 HTML 生图时，才切换到本地 HTML 截图模式。所有非照片类配图，默认按"SmartArt 风格的大字图形"处理，不做说明页式 PPT。联网下载规则见 [references/web-downloaded-images.md](references/web-downloaded-images.md)，API 规则见 [references/volcengine-seedream-images.md](references/volcengine-seedream-images.md)，本地规则见 [references/local-html-images.md](references/local-html-images.md)。
6.5 导出前统一规范图片目录。
   必须让 `article.md` 中的图片引用顺序与 `images/` 目录中的文件顺序一致；未被正文使用的图片移入 `_unused/`，避免用户人工辨别。`build_wechat_docx.py` 默认会自动执行这一步。
7. 导出最终 DOCX 成品。
   规则见 [references/wechat-docx-format.md](references/wechat-docx-format.md)。
7.5 默认导出顺序与自动行为。
   推荐顺序是先完成 `article.md` 和图片素材，再直接运行导出脚本。
   `build_wechat_docx.py` 在导出前会自动整理图片顺序、回写正文中的图片路径，并把未使用图片移入 `images/_unused/`。
   正常使用时，不应要求用户额外手动执行 `normalize_article_images.py`。
7.6 图片目录的完成态。
   `images/` 顶层只保留正文实际使用的图片，且文件名顺序应与正文中的引用顺序一一对应。
   候选图、淘汰图、下载缓存不应混在 `images/` 顶层；应放在 `_download_candidates/` 或 `_unused/`。

## 核心约束

- 默认使用 `scripts/generate_article_images.py`
- 默认使用 `scripts/build_wechat_docx.py`
- 导出前默认使用 `scripts/normalize_article_images.py`
- `scripts/normalize_article_images.py` 主要作为内部能力存在；正常使用时应由导出脚本自动触发，而不是要求用户手动调用
- API 生图密钥必须从项目根目录 `.env` 或系统环境变量读取；不要把真实 API Key 写入 skill 文件、参考文档或文章项目产物
- 写作与排版时都要主动控制标题长度：主标题不超过 17 个字，章节标题不超过 14 个字
- 写作时要主动控制段落长度，整体以"适中、不拖沓、适合手机阅读"为原则
- 文章必须有足够信息增量，不能写成稀薄的情绪稿、口水稿或只靠段落短来制造轻盈感的空稿
- 本地模式生成器名称固定为 `local-html`
- 本地图只接受 `html` 或 `html_path`，不再使用 SVG 或内置 layout
- 本地 HTML 图默认先按全画布设计；如果全视口会导致字小、留白过多或主体不饱满，就显式提供 `capture_selector` 按内容裁切输出
- 具体人物、公司、产品、地点或现场画面，优先考虑联网下载真实图片；抽象机制、判断关系和过渡页，优先考虑 API 图或本地解释图
- 非照片类配图默认追求 WPS SmartArt 一类的图形化表达：大字、少字、强结构、强留白，不做带解释段落的说明版 PPT
- SmartArt 默认优先这些结构：列表、流程、层级、矩阵、循环、堆叠；根据正文逻辑选一种，不要混搭
- 联网下载的图片必须先保存到本地并逐张视觉复核，确认主体正确、画面可用后再插入，不能只根据网页标题、alt 文本或文件名决定
- 找图尽量选横图，优先 16:9 或至少宽大于高；没有合格横图时，不要硬插竖图，改用 API 图或本地解释图
- 不要直接热链网页图片；最终插入 `.docx` 的必须是本地文件
- 本地图生成后必须逐张视觉复核，确认能在手机宽度下快速扫读
- 本地图生成后还要检查主构图覆盖率，不能只占中间一小块
- 如果视觉复核时发现「结构对了但字还是小」，或「上下留白多」，必须立刻大幅调高 HTML 字号、减小外层 padding 并配合 `capture_selector` 内容截取。
- 关键解释必须留在正文里，图片只做强调、转场、引导和记忆点。
- 正文解释概念时，不能只在概念层打转；至少要补一种具体化方式：真实公司案例、行业场景、用户动作、前后台流程、交易环节或日常生活类比。
- 单张图可见文字硬上限为 30 个汉字或等价字符，目标控制在 15 个字以内。
- **【移动端极致字号与留白限制】**：在 2560px 宽度画布下，主标题/数据字号必须在 **140px 到 240px** 之间，卡片/节点标题在 **72px 到 110px** 之间，正文/标签在 **48px 到 68px** 之间。绝对禁止任何小于 48px 的文字。外层容器 padding 须在 40px-60px 之间，默认显式在 JSON 中配置 `capture_selector: "[data-capture-root]"` 以便裁剪去除上下多余留白，最大化放大核心内容。
- **【排版密度与字号负相关黄金法则】**：图中字数越多，字号越受压制。如字号需调到 48px 以下才能塞下，必须强行删减文字只留 6-10 字以内的核心词标签。单栏/满宽布局字号为 `60px-85px`；双分布局（双卡片）字号为 `54px-72px`；三分布局（三卡片）字号为 `48px-60px`，单卡字数硬限 `8字`；四分布局（四卡片）字号为 `48px-54px`，单卡字数硬限 `6字`。绝对禁止放解释性长句，长句一律回归正文。
- 图中不要放完整解释句、长段落、小字注释、图例说明或卡片式补充文案；放不下就回正文。
- 如果一张图需要读者停下来读说明，说明这张图已经失败，必须重做。



## 导出命令

```bash
python3 scripts/generate_article_images.py output/短标题-MMDD/image-plan.json --output-dir output/短标题-MMDD/images
python3 scripts/build_wechat_docx.py output/短标题-MMDD/article.md output/短标题-MMDD/短标题.docx
```

默认理解：
- `build_wechat_docx.py` 会自动规范图片顺序
- 正常使用不需要手动调 `normalize_article_images.py`
