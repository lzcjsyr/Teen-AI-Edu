# 本地 HTML 解释图说明

这份说明只在用户明确要求本地生图时使用。
默认不要加载它。

## 什么时候用

- 用户明确要求本地生图、HTML 生图、解释图模式或可控图示
- 需要稳定中文标签、强结构、强可控的图
- 图片只承担强调、转场、引导，不替正文讲完整逻辑

默认仍然优先 API 生图。

## 基本规则

- 生成器写 `local-html`
- 只接受 `html` 或 `html_path`
- 默认 16:9 横图
- 默认先按全画布构图，再决定是否输出全视口；如果全视口会让字体变小或留白失衡，应改为内容裁切
- 默认视觉方向是 SmartArt，不是说明版 PPT
- 单张图文字硬上限为 30 个汉字或等价字符，最好 8 到 15 个字
- 最终插入文章的是截图后的 PNG/JPEG，不是 HTML 源文件
- 生成后必须逐张视觉检查，不合格就回改 HTML 重截
- **【移动端极致字号约束】**：在 2560px 宽度画布下，字号设计必须极为激进：
  - **超大数字/核心数据/大主标题**：必须在 **140px 到 240px** 之间
  - **节点名称/卡片标题/主要结论**：必须在 **72px 到 110px** 之间
  - **描述文字/次级标签/辅助正文**：必须在 **48px 到 68px** 之间
  - **绝对禁止出现任何小于 48px 的文字**（小于 48px 在手机端渲染后如蚂蚁般模糊，完全无法扫读）
- **【消除无意义上下留白】**：绝对禁止在图片上下留出大面积无意义的空白：
  - 容器的 `padding` 必须极为紧凑（上下 `40px` 到 `60px` 足矣），或将内容纵向撑满
  - **必须默认显式使用 `capture_selector` 指向主构图卡片 `[data-capture-root]` 进行紧凑内容裁剪**，裁剪时 `capture_padding` 设置在 `20px` 到 `35px` 之间，从源头上切除无用空隙，把核心内容放大到最大
- **【排版密度与字体字号的负相关黄金法则】**（设计规划时硬性遵守）：
  - **字数是字号的第一元凶**：图中的字数越少，字号才能拉得越大。当遇到「字号必须调小到 48px 以下才能塞下文字」时，**绝不允许妥协字号，必须强行删减文字，只留核心动宾短语或关键词标签，所有解释性长句一律回归正文**！
  - **布局分栏数（Column Split）与字号/字数的约束比例表**：
    | 布局分栏数 (2560px画布下) | 建议单栏字号范围 | 单栏极限字数上限 | 典型设计示例 |
    | :--- | :--- | :--- | :--- |
    | **单栏 / 满宽布局** (主容器 > 2000px) | **60px - 85px** | **15 字**以内 | 居中的大单结论、单行核心判断 |
    | **双栏 / 二分布局** (单卡片 ~ 1000px) | **54px - 72px** | **10 字**以内 | 二分数据对比、AB状态对照、两步流程 |
    | **三栏 / 三分布局** (单卡片 ~ 700px) | **48px - 60px** | **8 字**以内 | 三步环形闭环、三步并列流程、三支柱 |
    | **四栏 / 四分布局** (单卡片 ~ 500px) | **48px - 54px** | **6 字**以内 | 四象限判断矩阵、四支柱结构（慎用，易过载） |



## 截图策略

优先级固定如下：

1. 先用**全画布构图**，把主结构做大
2. 如果全视口输出已经足够饱满，就直接截全视口
3. 如果全视口输出导致字小、空白过多、主体不集中，就使用显式 `capture_selector` 按内容裁剪
4. 不要为了保持 16:9 而牺牲可读性；公众号里“有内容的图”比“硬凑固定比例的空图”更重要

不要把截图策略当成补救设计问题的第一选择。对公众号配图来说，最佳实践通常不是“先做一个很小的中心构图再靠裁剪救回来”，而是**一开始就把主要结构按 16:9 画布设计到足够大**。

默认要求：

- 主构图在视觉上应覆盖大部分横向空间
- 不要把真实内容压缩在中央一小块，四周留出大面积无意义空白
- 外层可以留安全边距，但不要再套一个很窄的 `max-width`
- 如果使用居中布局，也要让卡片、分栏、流程节点本身足够大
- 如果主构图已经够大，但全图仍然显得空，应优先裁掉外围空白，而不是继续缩小结构去迁就整张画布

脚本默认会检查 `[data-compose-root]` 的覆盖率并给出 warning。建议把真正的主构图容器标成 `data-compose-root`。

当你既想保留“按大画布设计”的灵活性，又想得到更饱满的最终图片时，推荐同时标两个根：

- `data-compose-root`：供脚本评估构图是否过小
- `data-capture-root`：供最终截图按内容裁切

两者可以相同，也可以不同。常见做法是：`data-compose-root` 覆盖整块版式，`data-capture-root` 只包需要输出的主内容区。

如确实要裁剪，可在计划项里显式提供：

```json
{
  "filename": "01-thesis.png",
  "html_path": "html/01-thesis.html",
  "capture_selector": "[data-capture-root]",
  "capture_padding": 40,
  "review_selector": "[data-compose-root]"
}
```

其中：

- `review_selector` 用于评估主构图是否过小
- `capture_selector` 只在你确定裁剪框稳定时才用
- 默认不启用裁剪，但只要视觉复核发现“字小、图空、内容不聚焦”，就应该启用

## 默认版式

优先使用下面这些高概括版式：

- 单结论：一个大标题，加一个很短的对照标签
- 二分关系：A / B、误解 / 现实、便宜 / 稀缺
- 列表结构：2 到 4 个横向或纵向并列块
- 堆叠结构：上中下、主次、前后台三层
- 三步流程：三个大节点加箭头
- 四象限或四支柱：每格只放 2 到 6 个字
- 层级结构：上位概念带 2 到 4 个分支
- 闭环关系：3 到 4 个大节点围成环

## SmartArt 选型

如果用户说“像 WPS/PPT 的 SmartArt”，默认从下面这些家族里选，不要自己发明复杂版式：

- 列表类：并列条目、分组列表、卡片列表
- 流程类：步骤、箭头、阶段推进
- 层级类：总分、树状、主次分叉
- 矩阵类：二分对照、四格判断、二维定位
- 循环类：闭环、反馈、往复增强
- 金字塔或堆叠类：由下到上、由表及里、能力分层

选型原则：

- 文章在讲“几个并列特征”，优先列表类或四支柱
- 文章在讲“先后顺序”，优先流程类
- 文章在讲“判断框架”，优先矩阵类
- 文章在讲“总论点和分支”，优先层级类
- 文章在讲“反馈闭环”，优先循环类
- 文章在讲“能力层次”，优先金字塔或堆叠类

默认不要做下面这些版式：

- 带整段解释文字的卡片墙
- 每个模块都有标题、描述、脚注的说明页
- 要靠小字读懂的图例、注释、备注区
- 像汇报 PPT 的“标题 + 四块说明文案”
- 一个图里混用两三种结构，导致视觉重心混乱

## 统一入口
优先使用统一入口脚本：

```bash
python3 scripts/generate_article_images.py /path/to/project-folder/image-plan.json --output-dir /path/to/project-folder/images
```

如果确定整批都走本地模式，也可以直接运行：

```bash
python3 scripts/generate_local_html_images.py /path/to/project-folder/image-plan.json --output-dir /path/to/project-folder/images
```

## 视觉检查

至少检查：
- 居中和对齐是否正常
- 文字是否出框、贴边或过密
- 对比度和配色是否清楚
- 主次层级是否一眼可读
- 手机宽度下是否还能快速扫读
- 最大字号是否足够大
- 主构图是否覆盖了画布的大部分区域
- 整体是否像 SmartArt，而不是说明版 PPT
- 图片是否存在“结构正确但信息区只占中间一小块”的问题
- 如果去掉外围空白后图片更强，是否应直接改为内容裁切输出

```json

  "images": [
    {
      "filename": "01-thesis.png",
```

## 支持的输入方式
1. `html`
   直接提供完整 HTML 或 HTML 片段，脚本会自动补外层文档并截图。
2. `html_path`
   提供一个 HTML 文件路径；完整文档直接截图，片段会先补外层文档。

## 写法要求
- 单张图只强调一个核心判断。
- 标签要短，尽量控制在 2 到 8 个汉字。
- 主标题尽量控制在 2 到 10 个汉字。
- 一个节点只放一个短标签，不要再跟一句说明。
- 默认节点数量控制在 2 到 4 个；超过 4 个通常说明这张图过载了。
- 当字看起来偏小，不要先加字解释；先删字、放大字、裁空白。
- 能用图形关系表达，就不要再补说明文字。
- 节点之间优先靠位置、箭头、连线、层级、底色分组表达关系。
- 不要把图片写成密集讲义页，也不要把字堆在某个角落造成版面失衡。
- 画面优先追求大字、均衡分布、留白、对比、停顿感，而不是信息总量。
- 主构图默认应占到画布的大部分区域；留白是为了呼吸，不是为了让内容缩成海报中间的一小块。
- 即使是本地模式，也不要让图片承担正文主论证。
- 写 HTML 时，要主动给文字、卡片、标签和装饰元素留安全边距，不要把版面写到刚好卡边。
- 除非有明确理由，避免在主构图容器上使用很窄的 `max-width`。
- 如果需要把一句完整的话塞进图里，先删；删不掉就把这句话放回正文。
- 视觉上如果像“海报贴在大幕布中间”，基本就是失败，需要重做版式或改用裁切。
